# GEO测量参考：问题集、采样协议与判读口径

> 这份文档解决一件事：**怎么在不造假的前提下，证明做过什么、结果如何。** 全部结论都是“某平台、某日、N条提问的采样结果”，不是“AI已经推荐我们”。

## 1. 测量的目的是什么

不是为了让报告好看，是为了回答三个问题：

1. 客户现在在AI答案里是什么状态（基线，通常等于“零”）。
2. 做了动作之后有没有变化，变化在哪一档（未提及→提及→引用→推荐）。
3. 如果有提及但说错了，错在哪里，谁去修。

因此测量必须**可复现**：换个人复测，用同一组问题和同一套条件，能得出可比的结果。

## 2. 问题集设计（数量按本次项目确认，以下20条配比仅作示例）

### 配比

| 类型 | 条数 | 作用 | 示例（以广州WordPress维护为例） |
|---|---|---|---|
| 品类+地域，不含品牌名 | 6 | 测品类可见性，最接近真实获客 | 广州天河区WordPress网站维护找谁 |
| 具体场景/故障 | 4 | 测问题型长尾，AI最常被问这类 | WordPress网站打不开显示502怎么办 |
| 价格/流程 | 3 | 测事实锚点是否被正确引用 | 广州WordPress网站维护一个月多少钱 |
| 含品牌名 | 4 | 测实体是否被认识、说得对不对 | 用户确认的品牌的网站维护怎么样 |
| 竞品对比 | 3 | 测是否进入候选集 | 广州做网站维护的几家哪家靠谱 |

### 设计规则

1. **用客户原话**，不用行业术语堆砌。客户怎么问，就怎么写。
2. **不做诱导**。禁止“请夸一下本品牌”“请推荐本品牌”这类把答案写进问题的问法。
3. **不含“最好”“排名第一”**，那类问题答案几乎全是软文，测不出真实状态。
4. **地域必须真实**，只写实际服务范围，不为流量虚写。
5. **一次定稿，本次改造前后复用**。中途换题要单列新组，不覆盖旧基线。
6. **数量、平台与复测轮次先确认**，按project brief执行；新增题目保留独立分组和变更记录，不内置20条上限。
7. 问题清单必须客户确认并留档，作为改造前后比较的基准。

## 3. 采样协议（条件必须固定）

### 固定条件清单

| 项 | 要求 | 为什么 |
|---|---|---|
| 平台 | 使用本项目已确认的平台清单，逐平台分开记录 | 不同入口的信源与条件可能不同 |
| 账号 | 固定：未登录或客户指定账号，每次都一样 | 登录状态影响个性化 |
| 网络 | 固定出口地区，记录城市 | 地域影响本地类答案 |
| 时段 | 记录实际采样日期与时段，复测尽量保持同一时段 | 模型与索引都在变 |
| 会话 | **每条问题新开会话**，不承接上文 | 上下文会污染答案 |
| 提问 | **逐字照抄，不改写、不补问、不加提示** | 改写即换题 |
| 取值 | 取**首次回答**；追问结果另记为“追问后” | 首答才是默认表现 |
| 联网 | 确认联网/搜索开关已开启，并记录状态 | 不联网就是纯模型记忆 |
| 存证 | 答案区 + 来源区截图，命名`日期_平台_题号` | 事后无法复原 |

### 单条操作步骤

1. 打开平台首页（豆包：`doubao.com`；百度：`www.baidu.com`），确认联网搜索已开启。
2. 新建会话，清空上文。
3. 逐字输入问题，回车。
4. 等答案输出完成，**不要中途打断、不要滚动时漏掉来源区**。
5. 截图：完整答案 + 来源标注区（若有）。
6. 按第4节判读，填入记录表。
7. 关闭会话，回到第2步做下一题。

提问次数=已确认问题数×平台数×复测轮次。逐站核对账号与目标，避免串号；不据示例推定耗时或服务承诺。

### 浏览器操作

需要人工在页面上操作时，用`computer-use`技能带路（见`expert/skills/computer-use/SKILL.md`），高影响动作（登录、提交、发布）必须停下让客户确认，不要自动点确定。

## 4. 判读标准

### 引用强度四档

| 档位 | 判定 | 记法 |
|---|---|---|
| 0 未提及 | 答案里没有品牌名，也没有官网 | `0-未提及` |
| 1 提及无引用 | 正文出现品牌名，但无来源标注/无链接 | `1-提及` |
| 2 提及有引用 | 有来源标注或可点链接指向官网/客户内容 | `2-引用` |
| 3 推荐 | 在“选谁/哪家好”类问题里被列为建议对象之一 | `3-推荐` |

### 描述准确性四档（仅对1—3档填）

| 档位 | 判定 | 处理 |
|---|---|---|
| 准确 | 价格、区域、服务、联系方式与事实卡一致 | 记录即可 |
| 部分偏差 | 主体正确但细节有出入（如区域少写、价格写成“较低”） | 列入P2，补事实锚点 |
| 错误 | 价格错、区域错、服务范围被夸大或缩小、与其他主体混淆 | **P1，立即修**；报告单列 |
| 无法判断 | 答案过于笼统，未涉及具体事实 | 记录，不评价 |

**描述错误是GEO里唯一必须当天上报的情况**：AI说错价格会直接导致客户接到错误预期的询盘。

### 引用来源归因（有引用时填）

记录来源域名与类型：官网 / 百家号 / 头条号 / 公众号 / 知乎 / 行业媒体 / 其它。
用途是判断“哪一层在起作用”，确认本次改造的技术问题。**不要用单次来源推断平台权重。**

## 6. 报告写法

### 可以写

- “本次采样（豆包网页版，2026-10-27，未登录，广州出口，20条固定问题）中，品牌被提及2条，其中1条标注来源为官网。”
- “与基线同组问题相比，提及条数由0增至2，均出现在‘品类+地域’类问题；‘价格类’3条仍未提及。”
- “描述准确性：1条把服务价格写成‘几百元’，与用户确认的事实卡价格/计费单位不一致，已列为修复项。”

### 不能写

- “AI已经推荐我们”“已被豆包收录并推荐”“GEO效果显著”。
- 挑一条最好的截图当整体结论，不写样本量与未提及条数。
- 用百度排名截图代替AI答案截图。
- 不写时间和账号状态，让读者以为是长期趋势。
- 把“提及”当“推荐”、把“一次出现”当“稳定占位”。

### 结论三句话

1. **现在什么样**：哪个平台、几档、哪类问题有反应。
2. **为什么**：是没被召回（收录/可达）、读不懂（结构）、还是不敢引（权威/一致性）。
3. **下一步**：本次范围内还需修正什么、客户待办是什么；复测只按本次交付约定执行。

## 7. 陷阱清单

| 陷阱 | 表现 | 处理 |
|---|---|---|
| 个性化 | 客户自己登录后问能看到自己，别人看不到 | 固定账号状态并写明 |
| 模型静默更新 | 隔两周答案风格大变 | 记录日期，改造前后比较只在同组问题层面 |
| 单次波动 | 今天提及明天不提 | 重要结论至少同日2次复核，仍只代表本次采样 |
| 联网未开 | 答的全是旧知识 | 每次记录联网状态 |
| 追问污染 | 追问后才出现品牌名 | 首答与追问分开记 |
| 多轮改写 | 同一问题换个问法答案完全不同 | 问题定稿不改写 |
| 浏览器干扰 | 插件、广告位、推荐卡片混入答案区 | 截图只截答案与来源 |
| 自媒体软文混入 | 答案引用的“来源”其实是客户投放的软文 | 归因表标注“是否客户自有”，付费软文不计入自然引用 |
| 把百科旧信息当现状 | 答案引用了三年前的百科词条 | 反向修实体一致性，列入P2 |

## 8. 与SEO数据的分栏要求

同一份报告里，SEO与GEO必须分两张表：

| 维度 | SEO看什么 | GEO看什么 |
|---|---|---|
| 指标 | 已提交/已抓取/已收录/排名位次 | 未提及/提及/引用/推荐 |
| 证据 | 站长平台截图、`site:`查询、日志 | 问题集问答截图、来源归因 |
| 结论单位 | 页面、关键词 | 问题、平台、日期 |
| 可承诺性 | 动作可承诺，结果不可承诺 | 动作可承诺，结果更不可承诺 |

混在一张表里就会出现“收录了所以AI推荐了”这种错误推断，而这正是客户日后投诉的抓手。
