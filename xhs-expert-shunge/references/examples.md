# 技术赛道写作范式

> 休眠素材：SKILL.md 未引用，不会自动加载。启用时在「模块路由」登记一行再删掉本句。

> 这里给的是**骨架 + 每句话的功能说明**，不是可直接发的成品。所有 `<占位:...>` 必须由作者填真实内容——工具名、版本、耗时、报错原文都不许用编造的填充。

## 一、先认清技术号的特殊性

| | 美妆/穿搭号 | 技术号 |
|---|---|---|
| 读者要什么 | 情绪 + 身份认同 | 一个能立刻用的东西 |
| 收藏动机 | "以后可能用得上" | "回头照这个做" |
| 涨粉逻辑 | 喜欢这个人 | 认可这个人的判断 |
| 最大风险 | 无聊 | 外行 |

结论：**技术号靠收藏起量，靠判断力涨粉。** 所以每一篇都要有一个"只有真做过的人才会说的细节"——具体的报错、具体的耗时、具体踩过的坑。这是唯一没法被搬运的东西。

## 二、塑料写法vs人味写法

同一件事，两种写法的差别不在文笔，在**信息密度和具体程度**。

| 塑料版 | 人味版 | 差在哪 |
|---|---|---|
| 今天给大家分享一个超好用的AI工具 | 这个工具我用了三周，只在一个场景下比ChatGPT强 | 有使用周期、有边界 |
| 它可以大幅提升效率 | 以前手改一遍要 <占位:分钟>，现在一条命令 | 有前后对照 |
| 安装非常简单 | 装的时候卡在 <占位:具体报错>，原因是 <占位:原因> | 有真实的坑 |
| 强烈推荐大家试试 | 适合 <占位:场景>，不适合 <占位:场景> | 有取舍 |
| 有问题评论区留言 | 你们的 <占位:环境/版本> 是什么？我这边在 <占位:版本> 上有差异 | 有具体的问 |

**改稿时只做一件事就够：把每句"很好用""很方便""很强大"换成具体到能验证的描述。**

## 三、三种常用骨架

### 骨架1：干货清单型（涨收藏主力，用户偏好）

```
<开头 2~3 行>
我 <占位:具体场景> 的时候一直 <占位:具体痛点，带数字>。
后来拆成 <N> 步，现在 <占位:结果，带数字>。
（不要写"随着AI的发展"这种背景铺垫，第一句就进场景）

<中段：N 条，每条 3~5 行>
1️⃣ <动作名，动宾结构>
   做什么：<一句话>
   怎么做：<命令/配置/步骤，要能直接抄>
   为什么：<不这么做会怎样——这句是同行判断你真做过的依据>

2️⃣ ...（同上，条目之间不要写过渡句）

<结尾>
<一句结论：这套东西的适用边界>
<一个具体问题：你们的 <占位:变量> 是怎么处理的？>
```

要点：
- 条目内部三行结构（做什么/怎么做/为什么）固定，读者扫读效率最高。
- 每条都要有"为什么"，这是干货和废话的分界线。
- 结尾问具体问题，不要问"你学会了吗"。

### 骨架2：踩坑复盘型（涨粉最快，因为暴露了真实成本）

```
<开头>
<占位:一个具体的失败结果>。花了 <占位:时长>，最后发现是 <占位:一句话原因>。
（先给结论，不要按时间顺序从头讲）

<中段：按"我以为 → 实际 → 代价"三段推进>
我以为：<占位:原判断>
实际：<占位:真相，附报错/日志片段>
代价：<占位:浪费的时间/钱/数据>

<收尾>
正确做法：<占位:三行以内能照做的>
如果有人已经踩过：<占位:一个反常识提醒>
```

要点：
- 一定要给报错原文或日志片段（脱敏），这是可信度的来源。
- "代价"必须写，不写代价的复盘没有说服力。
- 不要写成"我学到了很多"这种总结，给可执行的做法。

### 骨架3：工具测评型（带货/引流用，慎写）

```
<开头>
<占位:工具> 上线了 <占位:时间>，我用它做了 <占位:一件具体的事>。
结论先给：<占位:适合谁，不适合谁>。

<中段：四段对比>
能做的：<占位:2~3 条，具体到功能>
做不到的：<占位:2~3 条，这条最重要，决定可信度>
和 <占位:对比对象> 比：<占位:一个维度上的具体差异>
成本：<占位:价格/时间/学习曲线>

<结尾>
<占位:我的取舍>
```

要点：
- "做不到的"必须写，只夸不贬的测评没人信。
- 不要写成参数罗列，参数官网都有。

## 四、标题写法（技术向）

有效的四类，按点击率大致排序：

1. **具体动作 + 具体结果**：`一条命令把日志体积压掉八成`（数字要真）
2. **踩坑 + 代价**：`这个配置我调了两天，原因是大小写`
3. **反常识判断**：`我不建议新手一上来就学框架`
4. **身份 + 场景**：`后端转AI，我踩过的三个坑`

无效的：`一文读懂xx`、`xx详解`、`xx入门教程`——这类标题在技术号里点击率低，因为读者默认"我能搜到更好的文档"。

**标题里出现工具名，务必大小写正确。** `PostgreSQL` 不是 `Postgresql`，`GitHub` 不是 `Github`。写错就是外行信号。

## 五、封面

- 大字 ≤12字，写**结论**不写主题。写"压掉八成"不写"日志优化"。
- 技术号封面不需要好看，需要**可读**：深色底 + 等宽字体 + 一个数字，比花哨设计有效。
- 有代码/终端截图的封面，注意脱敏。

## 六、标签

- 大流量（1~2个）：`#程序员` `#AI` `#独立开发`
- 垂直（2~3个）：`#Python` `#后端开发` `#自建服务`
- 精准（2~3个）：`#后端转AI` `#Nas折腾` `#一个人做产品`

技术号不要蹭美妆/穿搭类大词，跨赛道导流基本无效，还会打乱账号标签。
