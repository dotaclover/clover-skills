# 美食雷达

把「最好吃」这种主观问题，拆成可核对的事实：**店在不在、菜是不是它的、还开不开、多少钱**。主观评价留给用户，客观项必须查实。

完整闭环，不依赖其他技能。候选来源可以是用户直接报的店名、网页搜索、或联网 AI——AI 只是「提供线索的人」，不是证据，也不需要先跑任何审计。

## 该用 / 不该用

| 场景 | 判断 |
|---|---|
| 「江南西最好吃的炒牛河是哪家」 | ✅ 主场景，走完整流程 |
| 「这家还开着吗 / 值不值得专门跑一趟」 | ✅ 单店核验，只跑步骤 2 和 3 |
| 「这几家怎么选，我想吃宵夜」 | ✅ 时段判断是核心变量 |
| 「炒牛河怎么做」 | ❌ 菜谱问题，不需要落地精度 |
| 「帮我写个探店文案」 | ❌ 内容创作，走对应工坊 |
| 「全国哪里的牛河最好吃」 | ❌ 范围无限大，结论无意义，先圈城市和商圈 |

## 一、前置条件（缺一项就先补，不要硬跑）

### 1. WorkBuddy 已连接浏览器

调 `browsers_list`，找 `type: "extension"` 的实例，记下 `browser_id`。找不到就停，让用户到扩展管理页确认已启用并「信任」。**不要**改用桌面端托管浏览器——那是另一个身份，没有用户的登录态。

### 2. 目标站点已预先登录

| 站点 | 未登录时的表现 | 处理 |
|---|---|---|
| 大众点评 | 评分能看，商户详情/部分评论/榜单会跳登录或滑块 | 停下让用户扫码，**不要替用户登录** |
| 高德 / 腾讯地图 | POI 基本免登录，适合查营业状态和电话 | 可直接用 |
| 小红书 / 抖音 | 只能拿标题，笔记正文和视频描述看不到 | 有登录态才有价值 |

判定方法：页面右上角出现「登录」= 未登录；显示头像/用户名 = 已登录。**先截图确认再操作**，别假设。

### 3. 本地 Python（用于 radar.py）

零第三方依赖，标准库即可，3.8+。PATH 里没有 `python` 时依次试 `python3` / `py -3`，或 WorkBuddy 托管解释器（位于 `<WorkBuddy 数据目录>/binaries/python/versions/<版本>/python.exe`，版本号因安装而异，不要硬编码）。都找不到就放弃脚本，走 `references/manual.md`，流程照样完整。

### 4. 先读 `references/browser-capabilities.md`

浏览器这一层有硬缺口（**不能执行 JS、不能抓网络层、不能并发**）。不先读这一节，很容易设计出「用 `innerText` 一次取全文」这种做不到的步骤，然后在执行中反复试错。

## 二、输入三要素（缺一个就问，不要猜）

| 要素 | 例 | 没给会怎样 |
|---|---|---|
| 城市 | 广州 | 会推荐到同名异地店 |
| 商圈/街道 | 江南西 | 「最好吃」范围无限大，结论无意义 |
| 品类/菜名 | 炒牛河 | 无法判断「招牌菜是否真是这道」 |

可选但显著提升命中率：**时段**（早餐/午市/宵夜）、**人均预算**。

## 三、执行流程

> **路径约定**：下文 `scripts/radar.py` 指本技能目录下的该文件，执行时拼成绝对路径。
> 数据默认存在**当前工作目录**下的 `.food-radar/`，跟着项目走——换项目就是另一个池子。

### 步骤 0 · 建池

```bash
python scripts/radar.py init --city 广州 --area 江南西 --dish 炒牛河 --budget 60
```

数据落在当前工作目录 `.food-radar/广州_江南西_炒牛河.json`。同名文件已存在时加 `--force` 覆盖。

### 步骤 1 · 收集候选（4–6 家，不要贪多）

三个来源可混用，**没有先后要求**：

1. **用户直接给的店名** —— 最快，直接进核验
2. **网页搜索** —— 关键词 `城市 + 商圈 + 菜名`，从摘要里挑出店名
3. **问联网 AI** —— 当线索提供者，不当证据

对来源的处理原则：

- AI **关闭搜索**给出的答案只作参考。实测中它会把别处的同名店安到目标商圈（把黄埔的店说成江南西的），而且语气比联网时更笃定。**这类答案必须逐店搜地址，搜不到直接判负。**
- AI 联网答案里如果自己写了「⚠️ 不在 XX 核心」，是它做的范围校正，可信度反而更高。
- 一个来源给 6 家以上就截断。核验成本才是瓶颈，不是候选数量。

### 步骤 2 · 逐店核验（核心环节，每家 3–5 次工具调用）

**取数顺序**（从省力到费力，命中就停）：

| 顺位 | 做法 | 能拿到什么 |
|---|---|---|
| 1 | `WebSearch` `店名 + 商圈 + 菜名 + 地址` | 地址门牌、人均、招牌菜描述。最快，先试这个 |
| 2 | 浏览器开大众点评商户页 → **截图** | 评分、评论数、口味/环境/服务、营业时间、招牌菜。该站评分数字是加密字体，直接读文本会得到乱码，用截图识别更可靠 |
| 3 | 浏览器开高德/腾讯地图 POI → 截图 | 营业状态（「营业中」/「暂停营业」）、电话、门牌 |
| 4 | 电话确认 | 终极手段。问「现在开吗、目标菜还有吗」 |

**点评页操作要点**（实测有效）：

1. `tabs_new` 直接开店名搜索 URL，**不要**在首页搜索框一步步点
2. 先 `tab_screenshot` 确认是否撞了登录墙或滑块
3. 撞滑块 → 立刻停，转 `WebSearch` 抓摘要。**不要反复刷新**，越刷越容易被封
4. 需要往下看时：先 `cua_click` 点正文空白处让焦点离开输入框，再 `dom_cua_keypress` 发 `PageDown`。`cua_scroll` 在这类长页面上经常超时

**四项硬核验**（缺一项就标「未确认」，不许猜）：

| 项 | 判据 | 红线 |
|---|---|---|
| **地址** | 精确到门牌号 + 参照物 | 只给「XX 大街一带」= 未确认；门牌与所说不同 = 记错 |
| **招牌菜归属** | 该店菜单/点评里，目标菜是否被反复提及为招牌 | 店是真的但招牌是烧鹅/肠粉，被硬说成「炒牛河首选」= **招牌错配，一票否决** |
| **人均** | 点评人均或菜单价 | 与声称差 >50% 记「价格存疑」 |
| **营业时间** | 商户页 + 电话 | **只做宵夜的店白天去会扑空**，这条最容易被漏 |

### 步骤 3 · 落库

每核验完一家立刻写进去，不要攒到最后——攒着一定会记混。

```bash
python scripts/radar.py add \
  --name 华叻强面家 \
  --address "紫龙大街24号之9" --landmark "紫丹阁对面" \
  --avg-price 23 --hours 07:00-22:30 \
  --rating 7.6 --review-count 729 \
  --signature yes --source 豆包 --data-date 2026-10 --area-confirmed
```

| 参数 | 说明 |
|---|---|
| `--signature yes/no/unknown` | 目标菜是否该店招牌。**`no` 会直接判出局** |
| `--hours` | 支持 `17:00-02:00`（跨零点）、`11:00-14:00,17:00-21:00`（多时段） |
| `--area-confirmed` | 人工已确认该店在本商圈。地址用街道名（紫龙大街 24 号）不含商圈名时会误报警，核验过就加上 |
| `--source` | 候选来源，出表时标注，便于回溯是哪家 AI 说的 |
| `--branch` | 连锁必须填，否则分店评分会混在一起 |
| `--data-date` | 数据时点。早于 2 年前会自动提示「价格/时间可能失效」 |

改字段用 `update --name 店名 --字段 新值`。查进度用 `list`。

### 步骤 4 · 判定与出表

```bash
python scripts/radar.py report                    # 打印决策表
python scripts/radar.py report --out 决策表.md     # 顺便存文件
```

脚本自动完成这些，不用手算：

- 四项核验计数，出局项（招牌错配 / 四项全无确认）单独列出
- 营业时间解析成时段覆盖（早/午/晚/宵夜），跨零点正确归到宵夜
- 排序按**可落地度**优先（确认项数 → 评分 → 评论数），不按「说得多好听」
- 地址不含商圈名、数据过期、缺营业时间等进「待人工确认」区

### 步骤 5 · 出结论前过一遍排坑清单

- **同名异地**：最常见的幻觉。搜到的店在另一个区/另一个城市，被安到目标商圈。
- **分店混淆**：同品牌多店，评分和营业时间常常不同，必须锁到「XX 店」。
- **旧数据**：2022 年及以前的点评，价格和营业时间基本失效；只有「是不是老店」这类结论不随时间变。
- **连锁误判**：全国连锁在本地榜单里评分通常 7 分左右，不代表「本地最强」。
- **SEO 软文**：标题带「3 个维度拆解 + FAQ」「人均 N 元起」的，一律不作为证据。
- **地图 POI 当评价**：地图条目只证明「存在」，不证明「好吃」。

## 四、输出模板

```
## 一句话结论
（时段 + 店名 + 点什么 + 人均）

## 决策表
| 时段 | 店 | 地址（门牌） | 人均 | 招牌 | 注意 |

## 核验明细
| 候选 | 来源 | 地址 | 招牌 | 人均 | 营业 | 确认 | 评分/评论 |

## 没排上的 & 为什么
（同名异地 / 招牌错配 / 数据过期 / 已停业）

## 待人工确认
（缺哪一项、需不需要打电话）
```

`radar.py report` 的输出就是这个结构，可直接贴给用户，但**要补一句人话结论**——脚本只能排可落地度，判断不了「哪家更合你口味」。

## 五、已知坑（实测，2026-10）

- **`cua_execute` 没有 JS 执行能力。** 别指望 `document.body.innerText` 一键取全文，想省截图次数只能靠 `dom_cua_get_visible_dom`。
- **`tab_id` 跨对话轮次会失效。** 每次操作前 `tabs_list`，不要复用旧 id。
- **输入框有焦点时 `PageDown` 滚不动页面。** 必须先点正文空白处。
- **`cua_scroll` 在长页面上频繁超时。** 用「点空白 → PageDown」替代。
- **点评页撞滑块一次就够。** 别硬刚，转 `WebSearch` 抓摘要，并标注「未取到站内实时评分」。
- **地址用街道名不含商圈名是常态**（紫龙大街、杏园大街都不含「江南西」）。别把它当成异地证据，核验过加 `--area-confirmed`。
- **只做宵夜的店是最大陷阱。** 17:00 才开门的店白天推荐等于让人跑空，营业时间必须查。
- **公众号探店文常把人均写成「人均 20+」。** 交叉两个来源再定。
- **AI 关搜索后给的答案更短、更笃定、更错。** 这种「确定性」来自幻觉，不来自证据。
