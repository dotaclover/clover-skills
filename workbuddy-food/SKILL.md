# 美食雷达

把「最好吃」这种主观问题，拆成可核对的事实：**店在不在、菜是不是它的、还开不开、多少钱**。主观评价留给用户，客观项必须查实。

完整闭环，不依赖其他技能。候选来源可以是用户直接报的店名、网页搜索、或联网 AI——AI 只是「提供线索的人」，不是证据，也不需要先跑任何审计。

**v1.1 变化**：开工先分流本地/云端；本地要正确打开带登录态的 Edge；缺扩展或未登录改为「询问」而非直接停；判定拆成**一票否决**与**加权排序**两层，闸门项不许被口碑分赎回。

**v1.2 变化**：**放宽准入、全天视角、营业优先**。① 经营状态 `unknown` 不再一票否决——只要没被 L0 否决就进表，标注「未验活」并排后；② 查询不按「提问当下」筛，默认全天，`--hours` 支持「全天」，四段全覆盖就显示全天；③ 排序主键改为「营业已确认(`open`)优先」，组内再按 L1 可落地度；④ `closed` / `elsewhere` / 招牌错配 / 四项全无确认仍是 L0 硬闸门，口碑分不能赎回。

## 该用 / 不该用

| 场景 | 判断 |
|---|---|
| 「江南西最好吃的炒牛河是哪家」 | ✅ 主场景，走完整流程 |
| 「这家还开着吗 / 值不值得专门跑一趟」 | ✅ 单店核验，只跑步骤 2 和 3 |
| 「这几家怎么选，我想吃宵夜」 | ✅ 时段判断是核心变量 |
| 「炒牛河怎么做」 | ❌ 菜谱问题，不需要落地精度 |
| 「帮我写个探店文案」 | ❌ 内容创作，走对应工坊 |
| 「全国哪里的牛河最好吃」 | ❌ 范围无限大，结论无意义，先圈城市和商圈 |

## 一、步骤 −1 · 环境探测与路由（开工第一件事）

**先判断自己站在哪台机器上**，再决定能拿什么数据、结论要降几级。完整决策树和询问话术见 `references/environment-routing.md`（**开工前必读**）。

调 `browsers_list`，按结果分流：

| 探测结果 | 路径 | 动作 |
|---|---|---|
| 有 `type: "extension"` 实例 | **本地** | 记下 `browser_id` → 身份校验三查 → 逐站验登录态 → 正常跑 |
| 工具存在但只有 `managed`/`desktop` 实例 | **身份错误** | 拒绝使用（那是另一个身份，没有登录态）→ 按「未安装」询问 |
| 工具根本不存在（云端沙箱） | **云端** | 声明降级 + 结论强制降级，见下 |
| 扩展已连但站点显示「登录」 | **未登录** | 停下提示，**不替用户登录** |

### 两种「问」，不是「停」

| 情况 | 用 `AskUserQuestion` 给的选项 |
|---|---|
| **未安装／未信任扩展** | ① 安装并信任扩展（推荐）② 走云端降级（明确告知损失）③ 我自己复核（`manual.md`） |
| **已连但没登录** | ① 我去登录，继续（推荐）② 跳过该站，转 `WebSearch`（损失写进结论） |

判定口径：右上角是头像/用户名 = 已登录；出现「登录」按钮、扫码框、撞滑块 = 未登录。**先截图确认再操作**，别假设。撞滑块一次就停，不要反复刷新。

### 本地：正确打开那台 Edge

三路 AI 线索用 `tabs_new` 直接开 URL，不要在首页搜索框一步步点：

| 站点 | URL |
|---|---|
| 豆包 | `https://www.doubao.com/chat/` |
| 元宝 | `https://yuanbao.tencent.com/` |
| DeepSeek | `https://chat.deepseek.com/` |

每站跑「联网开／联网关」两版共 6 份答案，只提取店名，地址和评价一律不采信。每轮操作前 `tabs_list` 重拿 `tab_id`。**身份校验三查**（`type=extension`、右上角是头像、能读到需登录才可见的内容）全过，才算正确打开了带登录态的 Edge；任一不过，拿到的评分和营业状态都不能当证据。

### 云端：降级必须传导到结论

硬规则（详见 `references/environment-routing.md` §四）：

1. **禁止把「页面/POI/词条还在」当成「店还开着」**——缓存可能停在 2022 年，闭店公告不会自动标进摘要。
2. 所有候选 `status` 默认 `unknown`；只有近 3 个月明确在营证据才允许写 `open`。
3. 逐店补一轮闭店检索：`店名 + 闭店/停业/歇业/搬迁/转让 + 近一年`，看到公告直接 `--status closed`。
4. 口碑数据超 12 个月不计入排序；`status=unknown` 仍可进表，但必须标「未验活」并排在所有 `open` 之后。
5. 输出写明「未取到站内实时评分与营业状态」；**首选只从 `open` 里选并附电话**，全是 `unknown` 时不给首选、只给排序线索并注明出门前验活。
   > ⚠️ 只写免责声明、结论却把「未验活」写成「现在能去」= 违规。

## 二、输入三要素（缺一个就问，不要猜）

| 要素 | 例 | 没给会怎样 |
|---|---|---|
| 城市 | 广州 | 会推荐到同名异地店 |
| 商圈/街道 | 江南西 | 「最好吃」范围无限大，结论无意义 |
| 品类/菜名 | 炒牛河 | 无法判断「招牌菜是否真是这道」 |

可选但显著提升命中率：**时段**（早餐/午市/宵夜）、**人均预算**。**不指定时段就按全天出表**，脚本不按提问当下的时刻筛选；指定时段只用于人工二次筛，不会把店从表里删掉。

## 三、执行流程

> **路径约定**：下文 `scripts/radar.py` 指本技能目录下的该文件，执行时拼成绝对路径。
> 数据默认存在**当前工作目录**下的 `.food-radar/`，跟着项目走——换项目就是另一个池子。

### 步骤 0 · 建池

```bash
python scripts/radar.py init --city 广州 --area 江南西 --dish 炒牛河 --budget 60
```

数据落在当前工作目录 `.food-radar/广州_江南西_炒牛河.json`。同名文件已存在时加 `--force` 覆盖。

### 步骤 1 · 收集候选（4–6 家，不要贪多）

三个来源可混用，**没有先后要求**：

1. **用户直接给的店名** —— 最快，直接进核验
2. **网页搜索** —— 关键词 `城市 + 商圈 + 菜名`，从摘要里挑出店名
3. **问联网 AI** —— 当线索提供者，不当证据。**本地路径**按步骤 −1 在 Edge 里开豆包/元宝/DeepSeek，各跑联网开/关两版；**云端路径**没有这条通道，只能靠网页搜索，且要主动补一轮闭店检索

对来源的处理原则：

- AI **关闭搜索**给出的答案只作参考。实测中它会把别处的同名店安到目标商圈（把黄埔的店说成江南西的），而且语气比联网时更笃定。**这类答案必须逐店搜地址，搜不到直接判负。**
- AI 联网答案里如果自己写了「⚠️ 不在 XX 核心」，是它做的范围校正，可信度反而更高。
- 一个来源给 6 家以上就截断。核验成本才是瓶颈，不是候选数量。

### 步骤 2 · 逐店核验（核心环节，每家 3–5 次工具调用）

**取数顺序**（从省力到费力，命中就停）：

| 顺位 | 做法 | 能拿到什么 |
|---|---|---|
| 1 | `WebSearch` `店名 + 商圈 + 菜名 + 地址` | 地址门牌、人均、招牌菜描述。最快，先试这个 |
| 2 | 浏览器开大众点评商户页 → **截图** | 评分、评论数、口味/环境/服务、营业时间、招牌菜。该站评分数字是加密字体，直接读文本会得到乱码，用截图识别更可靠 |
| 3 | 浏览器开高德/腾讯地图 POI → 截图 | 营业状态（「营业中」/「暂停营业」）、电话、门牌 |
| 4 | 电话确认 | 终极手段。问「现在开吗、目标菜还有吗」 |

**点评页操作要点**（实测有效）：

1. `tabs_new` 直接开店名搜索 URL，**不要**在首页搜索框一步步点
2. 先 `tab_screenshot` 确认是否撞了登录墙或滑块
3. 撞滑块 → 立刻停，转 `WebSearch` 抓摘要。**不要反复刷新**，越刷越容易被封
4. 需要往下看时：先 `cua_click` 点正文空白处让焦点离开输入框，再 `dom_cua_keypress` 发 `PageDown`。`cua_scroll` 在这类长页面上经常超时

**判定分两层**（v1.2）：**一票否决**只看闸门，**加权排序**只算可落地度。铁律仍是 **L0 不能被 L1 赎回**，但「经营状态未确认」已从闸门降为排序项——它不再让店消失，只让它排后并标注。

**第 0 项 · 经营状态（排序主键，不再是闸门）**

| 判据 | 红线 |
|---|---|
| 商户页「营业中／暂停营业」、近期闭店公告、电话确认 | **页面/POI/词条还在 ≠ 店还开着**。云端一律默认 `unknown`，只有近 3 个月明确在营证据才写 `open`；`unknown` 进表标「未验活」排后；确证闭店/停业/搬迁 `--status closed` 出局 |

**四项硬核验**（沿用，缺一项标「未确认」，不许猜；**属 L1 加权，不否决**）

| 项 | 判据 | 红线 |
|---|---|---|
| **地址** | 精确到门牌号 + 参照物 | 只给「XX 大街一带」= 未确认；门牌与所说不同 = 记错 |
| **招牌菜归属** | 该店菜单/点评里，目标菜是否被反复提及为招牌 | 店是真的但招牌是烧鹅/肠粉，被硬说成「炒牛河首选」= **招牌错配，升至 L0 一票否决** |
| **人均** | 点评人均或菜单价 | 与声称差 >50% 记「价格存疑」 |
| **营业时间** | 商户页 + 电话 | **只做宵夜的店白天去会扑空**，这条最容易被漏 |

| 层 | 包含 | 处理 |
|---|---|---|
| **L0 一票否决**（布尔，不打分） | 已闭店/停业/搬迁、招牌错配、同名异地确证、四项全无确认 | 直接出局，不进决策表，**不参与 score**；`status=unknown` 不在其中 |
| **L1 加权排序**（连续，只在 L0 通过者里算） | **营业已确认(+40，排序主键)**、确认项数、评分、评论数、数据新鲜度、地址精度、时段覆盖、来源交叉数 | 先按 `open` / `unknown` 分组，再按可落地度排；不排「说得多好听」 |

决策表准入：**未被 L0 否决即可进表**。排序：`open` 在前 → L1 得分高在前；`unknown` 标「未验活」排后。四项不全、招牌未确认只作提示，不再把店踢出去。首选只从 `open` 里挑。

### 步骤 3 · 落库

每核验完一家立刻写进去，不要攒到最后——攒着一定会记混。

```bash
python scripts/radar.py add \
  --name 华叻强面家 \
  --address "紫龙大街24号之9" --landmark "紫丹阁对面" \
  --avg-price 23 --hours 07:00-22:30 \
  --rating 7.6 --review-count 729 \
  --signature yes --source 豆包 --data-date 2026-10 --area-confirmed
```

| 参数 | 说明 |
|---|---|
| `--status open/closed/unknown` | **经营状态 = 排序主键**。`open` 排最前；`unknown`（默认）仍进表、标「未验活」排后；`closed`/`elsewhere` 一票否决 |
| `--signature yes/no/unknown` | 目标菜是否该店招牌。**`no` = 招牌错配，L0 一票否决** |
| `--last-seen` | 最近一次证实营业的时点，如 `2026-10` |
| `--hours` | 支持 `17:00-02:00`（跨零点）、`11:00-14:00,17:00-21:00`（多时段）、**`全天` / `24小时` / `00:00-24:00`** |
| `--area-confirmed` | 人工已确认该店在本商圈。地址用街道名（紫龙大街 24 号）不含商圈名时会误报警，核验过就加上 |
| `--source` | 候选来源，出表时标注，便于回溯是哪家 AI 说的 |
| `--branch` | 连锁必须填，否则分店评分会混在一起 |
| `--data-date` | 数据时点。超 **12 个月**口碑分自动不计入排序（防历史存档冒充现状），超 2 年另提示价格/时间失效 |

改字段用 `update --name 店名 --字段 新值`。查进度用 `list`。想看某家「为什么被否决／加权了多少」用 `explain --name 店名`。

### 步骤 4 · 判定与出表

```bash
python scripts/radar.py report                    # 打印决策表
python scripts/radar.py report --out 决策表.md     # 顺便存文件
```

脚本自动完成这些，不用手算：

- **L0 闸门先切**：已闭店/停业、招牌错配、同名异地确证、四项全无确认 → 直接出局，报告里标闸门类型，不参与打分
- **排序主键是营业状态**：`open` 组整体排在 `unknown` 组前面；组内再按 L1 得分（确认项数 → 评分 → 评论数 → 数据新鲜度，口碑超 12 个月不计分）
- **全天视角**：不按提问当下时刻筛；营业时间解析成时段覆盖（早/午/晚/宵夜），四段全覆盖显示「全天」，跨零点正确归到宵夜；缺时间的店标「未确认」但仍在表里
- 两分类出表：**决策表**（所有未被 L0 否决者，`open` 在前）／**没排上的**（L0 否决）；另列「待人工确认」提示哪些需电话验活
- `explain --name 店名` 打印单店的 L0/L1 分解，便于核对「到底是一票否决还是加权落后」

> **池子兼容**：v1.0 旧 JSON 没有 `status` 字段，读进来默认 `unknown`；v1.2 下这些店**仍会进表**，只是标「未验活」排后。用 `update --name 店名 --status open --last-seen YYYY-MM` 逐家补证据即可让它们排到前面；**云端一律留 `unknown`**，本地核实或电话验活后才写 `open`。`references/sample-pool.json` 可拿它跑回归。

### 步骤 5 · 出结论前过一遍排坑清单

- **同名异地**：最常见的幻觉。搜到的店在另一个区/另一个城市，被安到目标商圈。
- **分店混淆**：同品牌多店，评分和营业时间常常不同，必须锁到「XX 店」。
- **旧数据**：2022 年及以前的点评，价格和营业时间基本失效；只有「是不是老店」这类结论不随时间变。
- **连锁误判**：全国连锁在本地榜单里评分通常 7 分左右，不代表「本地最强」。
- **SEO 软文**：标题带「3 个维度拆解 + FAQ」「人均 N 元起」的，一律不作为证据。
- **地图 POI 当评价**：地图条目只证明「存在」，不证明「好吃」。

## 四、输出模板

```
## 一句话结论
（时段 + 店名 + 点什么 + 人均 + 本地/云端 + 是否需电话验活）

## 环境说明
（本地扩展已连 / 云端降级；未取到什么数据、结论降了几级）
```

## 五、已知坑（实测，2026-10）

- **`cua_execute` 没有 JS 执行能力。** 别指望 `document.body.innerText` 一键取全文，想省截图次数只能靠 `dom_cua_get_visible_dom`。
- **`tab_id` 跨对话轮次会失效。** 每次操作前 `tabs_list`，不要复用旧 id。
- **输入框有焦点时 `PageDown` 滚不动页面。** 必须先点正文空白处。
- **`cua_scroll` 在长页面上频繁超时。** 用「点空白 → PageDown」替代。
- **点评页撞滑块一次就够。** 别硬刚，转 `WebSearch` 抓摘要，并标注「未取到站内实时评分」。
- **地址用街道名不含商圈名是常态**（紫龙大街、杏园大街都不含「江南西」）。别把它当成异地证据，核验过加 `--area-confirmed`。
- **只做宵夜的店是最大陷阱。** 17:00 才开门的店白天推荐等于让人跑空，营业时间必须查。
- **公众号探店文常把人均写成「人均 20+」。** 交叉两个来源再定。
- **AI 关搜索后给的答案更短、更笃定、更错。** 这种「确定性」来自幻觉，不来自证据。
- **云端把「页面/POI/词条还在」当成「店还开着」是最贵的错。** 缓存点评页可能停在关店前，241 条历史评论会把已闭店老店推上首选（v1.1 实测事故）。
- **口碑分会把闸门项赎回来。** L0 未通过者绝不能进 L1 打分；老店评论多不等于还营业。
- **写了免责声明 ≠ 做了风控。** 限制必须传导到结论降级；只写「未取到实时状态」却照常输出 4/4 和首选，等于没降级。
- **连错浏览器实例**：`type: managed/desktop` 是另一个身份，没有登录态；用户坚称已登录但页面显示「登录」，就是连错了，回步骤 −1 重选 `browser_id`。
- **别把「未确认营业」当成「不推荐」。** v1.1 会因此把整张决策表清空；v1.2 起它只是排序项，标注后依然在表里，用户自己决定要不要打电话。
- **「全天」不等于 24 小时营业。** `--hours 全天` 是「四段全覆盖」的简写，写之前要确认店确实全天可去，别拿它给只做早午市的店兜底。
