# 浏览器能力边界（开工前必读）

结论基于实测（2026-10，Edge + WorkBuddy 扩展）。这一节决定流程怎么设计——设计错了会在执行中反复试错。

## 能做到（MCP 直接提供）

| 能力 | 工具 | 用途 |
|---|---|---|
| 开 tab / 跳 URL / 关 tab | `tabs_new` `tab_goto` `tabs_close` | 逐店开点评页 |
| 点击 | `cua_click`（坐标）、`dom_cua_click`（节点 id） | DOM 模式更稳，优先用 |
| 输入 / 按键 / 滚动 / 拖拽 | `dom_cua_type` `dom_cua_keypress` `cua_scroll` | 搜索框输入、翻页 |
| 截图 | `tab_screenshot`（可视区 / `full_page` / `clip` 裁剪） | 读渲染结果、验证是否登录 |
| 读可见 DOM | `dom_cua_get_visible_dom` | 拿到带节点 id 的文本树，可直接点 |
| 批量动作 | `cua_execute` | 一次提交「点击→输入→按键→截图」序列，减少往返 |

## 做不到（不要设计依赖它的流程）

| 缺口 | 后果 | 应对 |
|---|---|---|
| **不能执行 JS** | `cua_execute` 只支持坐标动作和截图，没有 eval 入口。拿不到 `document.body.innerText`，也读不到页面内嵌的 `__INITIAL_STATE__` 之类 JSON | 文字只能靠 `dom_cua_get_visible_dom` 或截图 |
| **不能抓网络层** | 无法读 XHR 响应、无法直接调商家接口 | 数据必须「渲染出来」才能取 |
| **不能并发** | 一个 tab 一次，10 家店 = 10 轮串行 | 候选控制在 4–6 家，核验成本才是瓶颈 |
| **tab_id 会跨轮次失效** | 复用旧 id 直接报 `tab does not exist` | 每轮先 `tabs_list` 重新确认 |

## 一个反直觉的结论：截图比读 DOM 更可靠

大众点评的评分、评论数用**自定义字体加密**：DOM 里是私有区字符（PUA），`innerText` 取到的是乱码方块。这时：

- 纯 DOM 方案 → 需要抓 woff、建字体映射表，工作量大且字体版本一变就失效
- **截图 + 多模态读图 → 直接读出来，零成本**

所以对点评类页面的取数策略是：**先用 DOM 定位和判断结构，关键数字用截图确认**。这不是退而求其次，是当前约束下的最优解。

## 需不需要辅助脚本

| 环节 | 谁来做 | 原因 |
|---|---|---|
| 开页面、点、翻、截图、读 DOM | **只在 WorkBuddy 里做** | 脚本碰不到这个浏览器通道；另起 Playwright 就没有用户的登录态 |
| 候选落库、四项判定、排序、出表 | **脚本 `radar.py`** | 浏览器采集是一轮一轮的散装调用，结果全散在对话里，聊到第 20 轮就丢了 |

结论：**脚本不替代浏览器操作，脚本替代的是「记性」和「算账」。** 取数靠 MCP，判定和沉淀靠脚本。

- 单家店核验：纯 WorkBuddy 完全够用，约 3–5 次工具调用
- 批量比价：必须靠脚本把数据固化，否则一定会乱
