# 排错手册

排错顺序固定：**看 HTTP 状态 → 看 `error.message` 原文 → 只改被指出的那一项 → 重试一次**。不要连换模型、连换地址地乱试，那是花钱买噪声。

## 一、按状态码

| 状态 | 典型 `error.code` / 文案 | 真实原因 | 动作 |
|---|---|---|---|
| 400 | `invalid_size`、`unsupported_value` | 该模型不支持这个 `size` / `quality` / `background` 组合 | 读 `error.param`，只改那一个字段，回落到 `1024x1024` 试 |
| 400 | `content_policy_violation` | 提示词或参考图触发内容审核 | 改写提示词，不要靠反复重试绕过 |
| 400 | `invalid_request_error` + 提到 multipart | `/images/edits` 用了 `application/json` | 改 `-F` 表单提交 |
| 401 | `invalid_api_key` | Key 错、带空格、多了 `Bearer ` 前缀 | 让用户重新核对，别猜新 Key |
| 403 | `model_not_allowed`、`insufficient_scope` | Key 有，但没有这个模型的权限分组 | 让用户在服务商后台看分组授权与模型授权 |
| 404 | `model_not_found` | 模型名错，或路径少了 `/v1` | 先 `GET /models` 拿真实名字 |
| 404 | 返回 HTML 页面 | 打到了前端，不是 API | 核对 base URL 与路由 |
| 413 | `payload_too_large` | 参考图超过服务商体积上限 | 压缩或缩放参考图到 25MB 内 |
| 415 | 无 | 提交了 JSON 给 multipart 路由，或反之 | 核对 `Content-Type` |
| 429 | `rate_limit_exceeded` | 并发或每分钟请求超限 | 看 `Retry-After`，退避后再试；**只重试一次** |
| 429 | `insufficient_quota`、`billing_hard_limit_reached` | 额度用完 / 账户欠费 | 直接告知用户，不重试 |
| 500 / 502 / 503 | `upstream_error`、`server_error` | 服务商侧故障或转发失败 | 隔 30 秒重试一次；连续两次失败就报故障，别硬刚 |
| 504 | 上游超时 | 图片还在生成但连接被判超时 | 先查是否已有结果；没有就放宽超时重提 |

## 二、按症状

### 出了文件但打不开

| 检查 | 命令 |
|---|---|
| 是不是 HTML / JSON 错误页 | `head -c 200 image-01.png` |
| 是不是 0 字节 | `ls -l image-01.png` |
| 文件类型 | `file image-01.png` |

开头是 `<` 或 `{` → 请求其实失败了，`-o` 把错误体存成了「图片」。回去看原始响应。

### `url` 有了但下载 403 / 404

签名 URL 过期，或需要带 Referer / UA。正确顺序是**生成后立刻下载**，不要隔一小时再取。下载失败就重新生成，别拿过期链接反复试。

### b64 解码报错

三种原因，按顺序排查：

1. 带了 `data:image/png;base64,` 前缀 → `split(",", 1)[-1]` 后再解。
2. 内容被截断（服务端响应体上限、被日志中间件截过）→ 看 `len(b64)` 是否明显偏小，改 `response_format: "url"` 或让用户换大文件下载方式。
3. Base64 里混进了换行或空格 → `base64.b64decode(s, validate=False)` 能容忍，`validate=True` 会直接抛错。

### 图片尺寸和请求不一样

服务端不支持该尺寸时**常静默回落成正方形**，不报错。生成后读 PNG 头（偏移 16 / 20）比对，不符就在报告里写明「实际 1024x1024，请求 1024x1536」。

### 要透明底，出图还是白底

两个条件必须同时满足：`background: "transparent"` **且** `output_format` 为 `png` 或 `webp`。只写 `background` 不生效的模型很常见；`jpeg` 永远没有 alpha 通道。

### 提示词里有文字，生成的是乱码或错字

模型渲染文字本身不稳，不是参数问题。做法：文字尽量少、短、用英文或数字；生成后逐字核对；错字就把「必须出现的文字」单独强调一遍重生成——但一次失败就够，别连试五张。

### 超时被杀，但又扣了钱

这是最常见的浪费。默认 120 秒前台超时会把 curl 杀掉（SIGTERM），服务端此时往往已经跑完并计费。

- 一律 `--max-time 480`，并放后台执行。
- 被杀之后先查落盘文件与原始响应，确认没出图再重提。
- 异步形态重新提交 = 重新排队 = 重新计费，能查就查。

## 三、兼容接口的常见差异

| 现象 | 原因 | 处理 |
|---|---|---|
| 传了 `model` 但出的图明显是另一个模型 | 服务端把不认识的模型名回落成默认模型 | 对比不同模型的出图风格与耗时，必要时让用户确认后台实际路由 |
| `response_format: "url"` 被忽略，仍返回 `b64_json` | 新版图像模型只支持 b64 | 两个字段都判空，别只写一个分支 |
| 返回里没有 `width` / `height` | 扩展字段可选 | 自己解码 PNG 头 |
| 返回 `"b64_json": ""` 但 `url` 有值 | 部分国产模型只给链接（实测 `qwen-image-3.0`） | 判空值再解码，改走 url 下载 |
| 400 报 `enable_interleave` / `messages` 这类陌生术语 | 该模型根本不走 OpenAI 协议（实测 `wan2.6-image`） | 换按服务商文档的请求体，别在 OpenAI 字段里硬试 |
| 签名链接过一阵变 403 / 404 | 对象存储签名到期（实测有效期约 24 小时） | 生成后立刻下载转存 |
| `/models` 里没有要用的模型 | 未开通，或服务端还没上架（如 `doubao-seedream-5-0-flash-260915`） | 先在服务商侧开通，别拼名字硬试 |
| 响应里多出 `usage`、`revised_prompt` 等字段 | 供应商扩展 | 只取需要的，不要按固定结构强解 |
| 同样的请求偶尔成功偶尔 502 | 转发不稳定或上游排队 | 有限重试一次，之后报故障 |
| 访问本机或内网服务 502 | 系统代理劫持了请求 | `--noproxy '*'`，或 Python 用空 `ProxyHandler` |
| `curl` 参数里的 `[` `]` 报错 | 某些 shell / 老版本 curl 把方括号当通配 | 加 `-g` 关闭 globbing |
| 中文提示词变问号 | 终端编码不是 UTF-8 | 请求体写成文件用 `--data-binary "@file.json"` |

## 四、报告失败时的写法

必须包含，不能省：

1. HTTP 状态码与 `error.code` / `error.message` **原文**。
2. 请求了哪个地址（host 可脱敏）、哪个模型、什么尺寸、`n` 是多少。
3. 已经排除的可能（例如「`/models` 返回 200，说明地址和 Key 都对」）。
4. 下一步需要用户提供什么（权限、额度、文档片段、一张真实响应）。

不要写「接口不支持」「模型不可用」这种把猜测当结论的话。没验证过的事，就说没验证。
