# 浏览器实拍

教程视频的可信度全靠这一段：**观众要看见它真的在跑**，不是听你说它能跑。

## 顺序：先查现场，再决定重录

录制前先看浏览器里有没有现成的会话（标签页、已登录状态、已经跑完的结果）。

- **页面还在** → 直接 claim 那个标签页，滚回开头重录一段，省掉几分钟的重新生成。
- **页面没了** → 才重新走一遍任务。这一步的结果数据必须来自这一次真实执行，不能套用旧的。

重录一段滚动，比重新跑一个两分钟的任务便宜得多，而且不会有"这次和上次结果不一样"的麻烦。

## 录制

```bash
# 1) 看窗口标题，确认命中哪一个
python scripts/record_window.py --list

# 2) 后台起录制（--duration 只作兜底）
python scripts/record_window.py --title "Edge" --duration 300 \
       --out episodes/EP01/rec/demo01.mp4 --stop-file episodes/EP01/build/stop

# 3) 操作（工具点击 / 键鼠脚本 / 手动）
# 4) 收尾：让 ffmpeg 自己写完末帧
touch episodes/EP01/build/stop
```

要点：

- **不要 kill 录制进程**。直接杀会让 mp4 的 moov 写不进去，文件打不开。用 `--stop-file`。
- 窗口会被最大化并置前，画面里只有这一个应用；想保留原窗口大小加 `--no-max`。
- gdigrab 只读像素，不抢焦点，录制期间可以正常操作。
- 默认不录鼠标（`--draw-mouse` 可开）。演示点击时鼠标其实有帮助，看风格定。
- 一次录**一个完整任务**，不要边录边分段；分段在 `beats.json` 里剪。
- 录制分辨率通常 1920×1080 或更大；渲染时 `resize_mode: contain` 会等比缩到画布，不会放大。

## 剪辑点：等待是证据，不是垃圾

实拍里大段等待（思考、读文件、写脚本）**不要剪掉**，压速就行：

| 内容 | 倍速 |
|---|---|
| 打字、点按钮、选文件 | 1.0–1.5 |
| 页面滚动、结果读取 | 1.0 |
| 等待执行、光标空转 | 2.5–4.0 |
| 长跑过程（>60s） | 4.0，并配一句"这段我压了速，真实两分钟" |

台词里要**主动交代压速**。观众发现你偷偷快进，比慢一点也不可信。

## 画面语言

- 讲哪一步，画面就停在哪一步；不要"画面上还在加载，嘴上已经讲结论"。
- 每段实拍的开头 0.3–0.5 秒给一个稳定画面，方便剪辑点对齐。
- 结果页至少停 2 秒（`end` 多留 2s），观众需要眼睛落地的时间。
- 浏览器缩放调到 100%，窗口最大化；缩放会糊。

## 素材管理

```
rec/
  EP01_DeepSeek_简报版.mp4        按 集号_工具_内容 命名
  EP01_DeepSeek_结论滚动.mp4
  EP01_WorkBuddy_发送执行.mp4
  EP01_WorkBuddy_结果.mp4
```

- 原片只读。不满意就重录一个新文件，不要覆盖旧的（旧的可能还有别的段在用）。
- 剪辑点在 `beats.json` 里写死 `start/end`，同一原片可以被多段引用。
- 录完先用 `probe` 看规格和时长，确认没录成 0 字节或帧率异常。

```bash
python scripts/video_pipeline.py --ffmpeg C:/ffmpeg/bin/ffmpeg.exe probe rec/demo01.mp4
```

## 常见问题

| 现象 | 处理 |
|---|---|
| 找不到窗口 | `--list` 看真实标题；浏览器标签页标题会覆盖窗口标题，用应用名（Edge/Chrome）匹配 |
| 录出来是黑屏 | 录到了受保护内容（DRM/硬件加速层），关掉浏览器硬件加速后重录 |
| 画面里出现别的窗口 | 录制前置前失败，重跑一次；或改用 `--no-max` + 手动摆位 |
| 文件打不开 | 被 kill 了，moov 没写完。用 `--stop-file` 重录 |
| 帧率不稳 | gdigrab 在 4K 全屏下会掉帧，降到 1080p 或 `--fps 25` |
